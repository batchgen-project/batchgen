## 3D-MoE port: on-disk vs minimax stacking assumption

The 3D-MoE port (`batchgen/models/glm/glm5/model.py:_init_fp8_blockwise_weights`)
stacks per-expert weights into 3D tensors assuming the minimax layout:

- `gate.weight` = `[N, K]` → stacked `[E, N, K]`   (N=moe_intermediate_size, K=hidden_size)
- `up.weight`   = `[N, K]` → stacked `[E, N, K]`
- `down.weight` = `[K, N]` → stacked `[E, K, N]`

If GLM-5's on-disk shapes below don't match this convention, the 3D stacking
is reinterpreting transposed weights and the FP8 blockwise GEMMs will silently
compute garbage — which is exactly what the post-port L2 run (3.9% accuracy)
exhibited.

| tensor                     | shape        | dtype   |
| -------------------------- | ------------ | ------- |
| gate_proj.weight           | [2048, 6144] | F8_E4M3 |
| gate_proj.weight_scale_inv | [16, 48]     | F32     |
| up_proj.weight             | [2048, 6144] | F8_E4M3 |
| up_proj.weight_scale_inv   | [16, 48]     | F32     |
| down_proj.weight           | [6144, 2048] | F8_E4M3 |
| down_proj.weight_scale_inv | [48, 16]     | F32     |

## Gotchas observed

### 1. 3D-MoE `buf.padded` must track `num_tokens_per_rank` per iter (2026-04-17)

**Symptom:** First L2 3D-MoE run landed at 3.9% accuracy (vs 71.9% baseline).
Most outputs were 30–40 tokens of degenerate garbage — structured patterns
like `## ## 1 ...`, `##3333...`, `ВQ: 0. 0. 0.`, cyrillic blocks. The shape of
the failure (peaked but wrong, not random) pointed at broken MoE activations.

**Root cause:** `buf.padded` was sized to `[init_num_tokens_per_rank, H]` at
`init_num_tokens()`, then `set_num_tokens_per_rank()` updated the
`self.num_tokens_per_rank` attribute but **did not resize `buf.padded`**.
PyNCCL `all_gather` at `distributed/device_communicators/pynccl.py:189` sends
`input_tensor.numel()` per rank. With `padded=[128,H]` and `ntp=8`, every rank
sent 128*H elements; the destination `all_tokens` slice `[:num_global=128]`
ended up holding only rank 0's padded tensor (8 real tokens + 120 zeros),
with ranks 1..15's tokens written to rows 128..2047 and never read.

**Fix:** in `Glm5MoE.set_num_tokens_per_rank()` (`batchgen/models/glm/glm5/model.py`),
resize `Glm5MoE._3d_buf.padded` to `[num_tokens_per_rank, H]` when the per-iter
value changes, mirroring `MiniMaxM25MoE.set_num_tokens_per_rank()` at
`minimax/minimax_m25/model.py:814-821`.

**Lesson:** when porting the K2.5 3D-MoE pattern to a new model, every place
the reference implementation resizes comm buffers must be ported too — the
initial allocation is sized for the max batch, but the send-buffer size is
taken from `input.numel()` at NCCL call time, not from `ntp * H`.
